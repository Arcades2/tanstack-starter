# Recherche : quelle lib i18n typesafe pour TanStack Start ?

Ticket : [#3](https://github.com/Arcades2/tanstack-starter/issues/3) (carte [#1](https://github.com/Arcades2/tanstack-starter/issues/1)).
Cette recherche alimente le ticket de décision [#13](https://github.com/Arcades2/tanstack-starter/issues/13) ; elle ne tranche rien.
État des lieux au 2026-11-23, versions relevées sur npm ce jour-là.

## TL;DR

- **Paraglide JS** est la seule lib que la doc TanStack Router/Start documente en détail, avec deux exemples officiels maintenus dans le dépôt TanStack et testés en e2e dans leur CI. Ses messages sont compilés en fonctions TypeScript : clés **et** paramètres sont typés sans configuration, et le code non utilisé disparaît du bundle.
- **i18next** et **Lingui** sont les plus matures et peuvent aussi être typesafe, mais avec plus de mise en place (i18next) ou un autre modèle (Lingui : textes sources dans le code, extraction, macro Babel).
- **use-intl** type les clés, mais le typage des paramètres repose sur le plugin Next.js, donc pas sur TanStack Start (non confirmé autrement).
- **Intlayer** a un guide TanStack Start complet mais un écosystème plus jeune, une évolution rapide (v9 en deux ans et demi) et un runtime plus lourd.
- **typesafe-i18n** : son auteur est décédé en 2023 ; le projet est repris par une organisation communautaire mais n'évolue presque plus. À éviter pour un nouveau socle.

## Ce que dit TanStack

Le guide officiel [Internationalization (i18n)](https://github.com/TanStack/router/blob/main/docs/router/guide/internationalization-i18n.md) de TanStack Router :

- Le routeur est **agnostique** côté lib. Il fournit les primitives : **paramètres de chemin optionnels** (`/{-$locale}/about` couvre `/about`, `/fr/about`…) et **réécriture d'URL** (`rewrite.input` / `rewrite.output`, voir [URL Rewrites](https://github.com/TanStack/router/blob/main/docs/router/guide/url-rewrites.md)).
- Il présente Paraglide comme « recommended pattern », avec deux exemples :
  [i18n-paraglide](https://github.com/TanStack/router/tree/main/examples/react/i18n-paraglide) (client) et
  [start-i18n-paraglide](https://github.com/TanStack/router/tree/main/examples/react/start-i18n-paraglide) (SSR avec Start).
- Il cite aussi en « autres intégrations » [Intlayer](https://intlayer.org/doc/environment/tanstack-start) et use-intl (via un billet de blog tiers, pas un exemple officiel).

Intégration Start + Paraglide d'après l'[exemple officiel](https://github.com/TanStack/router/tree/main/examples/react/start-i18n-paraglide) :
1. `npx @inlang/paraglide-js@latest init`, puis `paraglideVitePlugin({ project, outdir, strategy, urlPatterns })` dans `vite.config.ts`.
2. `rewrite: { input: deLocalizeUrl, output: localizeUrl }` dans `createRouter` pour les URL préfixées.
3. `server.ts` enveloppe le handler avec `paraglideMiddleware(req, ...)` (locale par requête en SSR).
4. `<html lang={getLocale()}>` dans `__root.tsx`.

Point d'attention : cet exemple déclare `@inlang/paraglide-js` `^2.4.0` alors que **Paraglide 3.0.0 est sorti le 2026-11-03** (dernière 3.2.2) ; l'exemple n'a donc pas encore été migré en v3 ([package.json](https://github.com/TanStack/router/blob/main/examples/react/start-i18n-paraglide/package.json)).

### Paraglide JS

- Compilateur : `messages/en.json` (ou `fr.json`) devient des fonctions `m.greeting({ name })` ; une faute de clé ou un paramètre manquant est une erreur TypeScript ([README](https://github.com/generaltranslation/paraglide-js#readme)).
- v3 (nov. 2026) : modules virtuels par défaut avec le plugin Vite, `.d.ts` générés directement (sans passer par TypeScript), builds jusqu'à 18x plus rapides que la v2 ([billet v3](https://github.com/generaltranslation/paraglide-js/blob/main/blog/v3/index.md), [CHANGELOG](https://github.com/generaltranslation/paraglide-js/blob/main/CHANGELOG.md)). Ruptures v3 : suppression de `additionalFiles` et de `experimentalMiddlewareLocaleSplitting`.
- Détection de locale par une liste de **stratégies** (`url`, `cookie`, `preferredLanguage`, `localStorage`, `baseLocale`, personnalisées) ([doc Strategy](https://github.com/generaltranslation/paraglide-js/blob/main/docs/strategy.md)). Une app mono-langue peut se contenter de `["baseLocale"]`.
- Pluriels et variantes via `Intl.PluralRules` et des sélecteurs façon MessageFormat 2 ([doc Variants](https://github.com/generaltranslation/paraglide-js/blob/main/docs/variants.md)).
- Convention de clés : la doc **recommande des clés aléatoires lisibles** (`penguin_purple_shoe`) plutôt que sémantiques (`login_button_label`), pour qu'elles restent stables ([doc Message Keys](https://github.com/generaltranslation/paraglide-js/blob/main/docs/message-keys.md)). Les clés sémantiques restent supportées ; c'est une convention à trancher dans #13.
- Le dépôt référencé par npm est désormais `github.com/generaltranslation/paraglide-js` (les badges du README pointent encore vers `opral`) : le projet a changé d'organisation GitHub, le paquet npm `@inlang/paraglide-js` reste le même.
- Inconvénient : le format de projet inlang (`project.inlang/settings.json` + plugins de format) ajoute un concept de plus. En SSR, la locale par requête passe par `AsyncLocalStorage` via `paraglideMiddleware` (runtime Node, compatible avec les fonctions Netlify).

### i18next / react-i18next

- Le standard de fait, énorme écosystème (backends, plateformes de traduction).
- Typesafe via un fichier de déclaration (`CustomTypeOptions.resources`), généré par `npx i18next-cli types` ou écrit à la main avec `as const` ; l'interpolation est vérifiée par défaut (`strictInterpolationChecks: true`). TypeScript 5 requis ; de grosses ressources peuvent ralentir le type-check ([doc TypeScript](https://www.i18next.com/overview/typescript)).
- Pas d'exemple TanStack officiel : SSR (instance par requête, hydratation des ressources) et routage par locale à câbler soi-même. Runtime le plus lourd du lot.

### Lingui

- Modèle différent : on écrit le texte dans le JSX (`<Trans>Welcome Home!</Trans>`, ``t`Bonjour ${name}` ``), `lingui extract` génère les catalogues (`.po`), `lingui compile` les compile. Pas de clés à nommer ni à taper ; les paramètres sont des variables JS, donc vérifiés par TypeScript.
- [Exemple officiel TanStack Start](https://github.com/lingui/js-lingui/tree/main/examples/tanstack-start) maintenu par Lingui : plugin Vite `lingui()`, macro via `@rolldown/plugin-babel`, et un `requestMiddleware` Start pour la locale.
- v6 (2026-04-22) : ESM uniquement, meilleur support TypeScript ([CHANGELOG](https://github.com/lingui/js-lingui/blob/main/CHANGELOG.md), [annonce](https://lingui.dev/blog/2026/04/22/announcing-lingui-6.0)).
- Inconvénients : dépendance à une transformation Babel dans une chaîne Vite/Rolldown, et un flux extract/compile à intégrer (CI, hooks). Pour une app mono-langue, c'est le seul candidat où le code reste lisible sans fichier de messages.

### use-intl

- Cœur framework-agnostique de next-intl, ICU, très utilisé.
- Clés typées via l'augmentation `AppConfig` ([source](https://github.com/amannn/next-intl/blob/main/packages/use-intl/src/core/AppConfig.tsx)). Le typage des **arguments** demande `createMessagesDeclaration`, une option du **plugin Next.js** ([doc TypeScript](https://next-intl.dev/docs/workflows/typescript)) : rien d'équivalent documenté pour TanStack Start.
- Pas d'exemple TanStack officiel ; la doc TanStack renvoie à un billet tiers.

### Intlayer

- Contenu déclaré dans des fichiers `*.content.ts` co-localisés aux composants (`t({ en, fr })`), types générés dans `.intlayer/`, routes sous `src/routes/{-$locale}/`, proxy de locale intégré au plugin Vite depuis la v9 ([guide TanStack Start](https://intlayer.org/doc/environment/tanstack-start)).
- Apache-2.0 ; un CMS hébergé et un éditeur visuel sont optionnels (le CMS est payant ou auto-hébergé).
- Inconvénients : projet jeune et porté essentiellement par un mainteneur ([dépôt](https://github.com/aymericzip/intlayer), ~870 étoiles), versions majeures fréquentes, runtime React plus lourd, plusieurs concepts propres (dictionnaires, proxy, compilateur, CMS).

### typesafe-i18n

- Très léger et entièrement typé, mais son créateur Ivan Hofer est décédé en 2023 ([README](https://github.com/codingcommons/typesafe-i18n#readme)). Le dépôt est passé chez `codingcommons` ; dernière version en février 2026, dernier push en mars 2026. Aucune intégration TanStack Start. Pas un bon pari pour un socle neuf.

## Coût d'avoir l'i18n dès le départ (app mono-langue)

Ce qui s'ajoute concrètement au starter avec Paraglide en mono-langue (d'après l'exemple TanStack et la doc des stratégies) :

- 1 dépendance, 1 plugin Vite, `project.inlang/settings.json`, `messages/fr.json`, un dossier généré (`src/paraglide`) à ignorer dans git et Biome.
- `strategy: ["baseLocale"]` : pas de middleware, pas de réécriture d'URL, pas de route `{-$locale}`. On ajoute ces trois éléments le jour où une deuxième langue arrive.
- Coût quotidien : chaque texte visible passe par `m.xxx()` et une entrée JSON au lieu d'une chaîne littérale. C'est la vraie friction, quelle que soit la lib (sauf Lingui, où le texte reste dans le JSX).
- Bénéfice : les textes sont déjà externalisés si une app dérivée devient multilingue. Les migrer après coup demande de reprendre tous les composants.

Alternative sans lib : textes en dur et routage `{-$locale}` natif le jour venu ; la doc TanStack montre ce schéma, mais sans typage des traductions ni pluriels.

## Recommandation (à valider dans #13)

La décision revient à l'humain, dans le ticket de grilling [#13](https://github.com/Arcades2/tanstack-starter/issues/13). Pour l'éclairer :

- **Si l'i18n est adoptée dès le starter : Paraglide JS v3.** C'est l'option la plus typesafe sans configuration (clés et paramètres), la plus légère en production, la seule documentée et testée par TanStack, et elle se réduit à presque rien en mono-langue (`baseLocale`). Points à surveiller : l'exemple TanStack est encore en v2 (à valider en v3 au moment de construire) et la convention de clés à choisir (aléatoires recommandées par Paraglide ou sémantiques).
- **Alternative à garder en tête : Lingui**, si on préfère garder les textes lisibles dans le JSX plutôt que gérer des clés ; en échange, macro Babel et étape extract/compile.
- **À écarter pour un nouveau socle** : typesafe-i18n (maintenance), use-intl (paramètres non typés hors Next.js). i18next reste viable mais apporte plus de câblage et de poids pour le même résultat.
- Questions ouvertes pour #13 : adopter dès le départ ou laisser aux apps dérivées ; clés aléatoires ou sémantiques ; un fichier de messages unique ou découpé ; routage par préfixe d'URL ou par cookie le jour où une 2e langue arrive.
